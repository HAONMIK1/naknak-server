# 100만 유저 트래픽 대비 아키텍처 (설계)

## 배경

지금까지는 기능 하나씩 만드는 데 집중했고, 인프라는 `infra/`(Terraform)를 보면 알 수 있듯
**전부 프리티어/비용최적 단일 노드**다.

- EC2 `t3.micro` 1대 (앱 컨테이너가 여기 하나에서만 돈다)
- RDS Postgres `db.t3.micro`, **단일 AZ** (Multi-AZ 아님, 읽기 복제본 없음)
- ElastiCache Redis **단일 노드** (클러스터 모드 아님)
- 프론트는 GitHub Pages 정적 호스팅(이건 그대로도 무한 확장됨 — CDN이라 걱정 없음)

즉 지금 상태로 트래픽이 커지면 **앱 서버 1대, DB 1대, 캐시 1대**가 전부 단일 장애점(SPOF)이자
스케일의 한계다. 100만 유저를 오늘 당장 준비할 필요는 없지만(비용 낭비), 트래픽이 늘 때 "다음에
뭘 먼저 손대야 하는지" 순서를 미리 정해두면 실제로 늘었을 때 허둥대지 않는다. 이 문서는 그
순서를 정의한다 — 지금 전부 구현하지 않는다.

## 이미 되어 있는 것 (스케일에 유리한 선택들)

인프라는 최소 규모지만, 코드 레벨에서는 이미 확장에 유리한 선택을 여럿 해뒀다.

- **JWT 기반 무상태(stateless) 인증** — 세션 스토어가 없어서 앱 서버를 몇 대로 늘려도 로드밸런서
  뒤에 그냥 붙이면 된다(sticky session 불필요).
- **팔로우 네트워크(촌수) 계산의 Redis 캐싱** — 재귀 CTE 결과를 캐싱해 반복 조회 비용 제거
  ([feed.md](feed.md)).
- **GLOBAL 랭킹의 Redis ZSET 캐싱** — 전체 유저가 보는 랭킹을 매 요청 `ORDER BY` 대신 O(log n)
  조회로 대체 ([score.md](score.md)).
- **점수 원장(`user_score_history`)이 append-only** — 감사용 로그 테이블이라 나중에 쓰기 전용
  파티셔닝/별도 저장소로 옮기기 쉬운 구조.

## 트래픽 단계별 로드맵

**"1단계"부터 순서대로 트리거 조건이 오면 그때 그 단계를 실행한다** — 미리 다 만들지 않는다.
각 단계 트리거는 대략적인 기준이며, 실제로는 모니터링 지표(아래 6번)로 판단한다.

### 1단계 — 지금 ~ 초기 사용자 (수백~수천 명)

지금 인프라 그대로 간다. 손댈 것 없음. 다만 아래 2가지는 지금 해도 비용이 거의 안 드니 미리
해두는 게 좋다.

- **Hikari 커넥션 풀 명시적 설정** — 현재 `application.yml`에 풀 크기 설정이 없어 Spring Boot
  기본값(10)을 쓰고 있다. `db.t3.micro`는 `max_connections`가 낮아서(대략 66개) 앱 인스턴스를
  늘리기 전에 먼저 이 숫자를 명시적으로 관리해야 한다.
- **N+1 점검** — 지금 리스트 API들(`ScoreService.usersById`, `FollowService.toFollowUserResponses`
  등)은 대부분 `findAllById`로 배치 조회하고 있어 N+1은 아니다. 새 기능 추가할 때마다 이 패턴을
  유지하는 게 중요 — 리뷰 수가 늘어날 API(피드, 랭킹)에서 특히.

### 2단계 — 수만 명, 트래픽 급증 초입 (RDS/Redis CPU가 자주 70% 넘을 때)

- **EC2 → ECS/Fargate(또는 Auto Scaling Group) 전환 + ALB** — 앱 서버가 1대에서 여러 대로
  늘어나는 시점. JWT 무상태 인증이라 이 전환 자체는 어렵지 않다.
- **RDS 인스턴스 클래스 상향 + Multi-AZ 전환** — 단일 AZ는 장애 시 다운타임이 생긴다. 이 시점부터는
  가용성이 비용보다 중요해진다.
- **RDS 읽기 복제본(Read Replica) 1대 추가** — 피드/랭킹/맛집 검색처럼 읽기가 압도적으로 많은
  쿼리를 복제본으로 분리. 코드 레벨에서는 읽기 전용 트랜잭션(`@Transactional(readOnly = true)`,
  이미 대부분 붙어 있음)을 라우팅 기준으로 활용할 수 있다.
- **S3 업로드 이미지 앞에 CloudFront(CDN) 추가** — 리뷰/맛집 사진이 지금은 S3 직접 서빙으로
  보인다. 사용자가 늘면 이미지 트래픽이 가장 먼저 커지는 부분이라 CDN 붙이는 게 비용 대비 효과가
  가장 크다.

### 3단계 — 수십만 명 (DB 쓰기가 병목이 되기 시작할 때)

**진행 상황 (2026-07-18)**: 아래 세 항목은 코드/Terraform 준비까지 끝났다. `user_score_history`
파티셔닝은 마이그레이션이 실제 적용됐고(V5), 나머지 둘은 **`terraform apply`를 아직 실행하지
않아 인프라에는 반영되지 않은 상태**다 — 실제 큐/클러스터가 생기기 전까지는 코드가 기존과
동일하게(동기 처리, 단일 Redis 노드) 동작한다.

- **Redis 단일 노드 → 클러스터 모드 전환** — 네트워크 캐시, 랭킹 ZSET, 블랙리스트/리프레시 토큰이
  전부 한 노드에 몰려 있다. 이 시점부터 단일 노드 메모리/처리량 한계에 부딪힌다.
  `infra/redis.tf`를 `aws_elasticache_replication_group`(샤드 2개 + 샤드당 복제본 1개, 자동
  페일오버)으로 준비해뒀다. **apply 시 애플리케이션의 Redis 연결 설정도 반드시 같이 배포해야
  한다** — 지금 코드는 `spring.data.redis.host/port`(단일 서버) 설정이라 클러스터 모드
  엔드포인트에는 그대로 못 붙는다(`spring.data.redis.cluster.nodes` 기반으로 바꿔야 함). 순서가
  어긋나면 앱이 Redis에 연결하지 못하므로, terraform apply와 애플리케이션 배포를 한 세트로
  묶어서 진행해야 한다.
- **점수 적립(`ScoreService.earn`)을 비동기화** — 지금은 리뷰 작성 요청 하나가 리뷰 저장 + 점수
  적립(DB 쓰기 2번 + Redis 쓰기 1번)을 동기로 다 처리한다. 트래픽이 커지면 리뷰 작성 API의
  응답 지연으로 이어진다. `ScoreEarnPublisher`로 추상화해서, SQS 큐가 설정된 환경(운영)에서는
  이벤트만 던지고 `ScoreEarnConsumer`가 별도로 처리하며, 설정 안 된 환경(로컬/테스트)은 기존과
  동일한 동기 직접호출로 폴백한다 (docs/score.md 참고). `infra/sqs.tf`로 큐 + DLQ를 준비해뒀지만
  apply 전까지는 `aws.sqs.score-earn-queue-url`이 어떤 환경에도 없어 동기 폴백만 동작한다.
- **`user_score_history` 파티셔닝(월별)** — append-only 로그 테이블이 가장 빨리 커지는 테이블이다.
  월별 파티션으로 나눠두면 오래된 데이터 조회/삭제가 최근 파티션에 영향을 안 준다.
- **네이버 검색 API 사용량 관리** — 무료 API 호출량은 제한이 있다(개발 중 이미 rate limit을
  겪음). 맛집 등록이 늘면 이 한도에 먼저 걸릴 수 있으니, 캐싱(같은 이름+주소 재검색 방지, 이미
  일부 구현됨) 외에 API 사용량 모니터링과 유료 등급 전환 검토가 필요하다.

### 4단계 — 100만 명 근접 (DB 자체가 한계에 부딪힐 때)

- **읽기 복제본 다중화 + 캐시 우선 전략 강화** — 피드/랭킹은 거의 전량 캐시에서 응답하고, DB는
  캐시 미스/쓰기 전용으로 취급.
- **핵심 테이블 샤딩 검토** — `reviews`, `follows`, `user_score_history`처럼 유저 수에 비례해
  커지는 테이블은 `user_id` 기준 샤딩을 검토한다. 다만 팔로우 그래프의 재귀 CTE는 샤딩과 상성이
  나쁘다(그래프 탐색이 샤드를 넘나듦) — 이 시점엔 네트워크 촌수 계산을 그래프 전용 스토어(Neo4j
  등)로 분리하는 것도 후보.
- **APM/분산 트레이싱 도입** — 여러 서비스/큐로 나뉘기 시작하면 요청 하나가 어디서 느려지는지
  추적하기 어려워진다. 이 시점부터는 필수.

## 지금 당장 할 만한 것 (선택)

전체 로드맵과 별개로, 비용 부담 없이 지금 해두면 나중에 편한 것 두 가지만 고르면:

1. Hikari 풀 크기 명시적 설정 (RDS 커넥션 한도 보호)
2. S3 이미지 앞단 CloudFront (지금도 이미지 로딩 속도 체감 개선 + 나중 CDN 전환 비용 없음)

나머지(ECS 전환, Read Replica, 큐 분리, 샤딩)는 실제 트래픽 신호가 보이기 전에는 만들지 않는다 —
지금 만들어봤자 검증할 트래픽이 없어서 오히려 운영 복잡도만 늘어난다.
